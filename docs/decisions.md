# Decisions

Decisions taken while executing `PLAN.md` that were not covered by `docs/design.md` or the plan, and adaptations of items marked **[VERIFY]**. Newest last.

| # | Phase | Decision | Reason |
| --- | --- | --- | --- |
| 1 | 0 | All tools are invoked as `uv run ast-grep ...`, never as `sg`. | On many Linux systems `sg` is the shadow-utils `setgroups` binary (it is on this machine: `/usr/bin/sg`). |
| 2 | 0 | `pre-commit` is a dev dependency managed by `uv`, not a global install. | `make setup` must work on a fresh machine with only `uv`. |
| 3 | 0 | `[tool.uv] package = false`: the repo is not an installable package; the fixture code (`fixtures.valid`) is imported from the repo root. | Simplest option; `lint-imports` and `pytest` run from the root. |
| 4 | 1 | Verified the Cursor rule format: `.mdc` files under `.cursor/rules/` with `description`, `globs`, `alwaysApply` frontmatter (cursor.com/docs/context/rules). Unchanged from the plan. | [VERIFY] item. |
| 5 | 1 | `naming.mdc` has no folder in `fixtures/invalid/`. `domain_imports_infra.py` is not expected to produce an ast-grep finding; it is verified by the import-linter test instead. | Judgment rules have no deterministic check, and the architecture rule is enforced by import-linter, not ast-grep. |
| 6 | 1 | Dropped the `prefer-pydantic-over-dataclass` check and its invalid fixture; `python-models.mdc` now prefers Pydantic but allows `@dataclass` when required. | PR #3 review: dataclasses should be allowed when required, not banned. |
| 7 | 1 | Fixtures live under one `fixtures/` folder: `fixtures/valid/` (was `example_app/`, must pass every check) and `fixtures/invalid/<rule>/` (was `demo/violations/`, one folder per `.mdc` rule, must be caught). Kept in this repo, not a submodule. `make demo` keeps its name. | PR #3 review: one folder for all fixtures. `valid`/`invalid` matches ast-grep's rule-test keys; `pass` is a Python keyword and could not be imported. A submodule would split every rule change across two repos. The folder layout replaces the file-to-rule table. |
| 8 | 2 | Verified Python node names with `--debug-query`: a bare `except:` is an `except_clause` without a `value` field; `except Exception as e:` has `value: as_pattern`. ast-grep does not accept regex in `kind`, so "has a value" is written as `has: {field: value, regex: "."}`. | [VERIFY] item. |
| 9 | 2 | `ast-grep test` runs with `--skip-snapshot-tests`. Valid cases must not match and invalid cases must match; label snapshots are not stored. | Snapshots pin highlight ranges, not behavior, and every generated check would need a regenerated snapshot. Verified that a non-matching invalid case still fails. |
| 10 | 2 | `files`/`ignores` globs are matched against the path exactly as passed on the command line (relative to the cwd; absolute paths do not match `fixtures/**`). Rules use `**/<folder>/**` globs so both relative and absolute paths (as sent by agent hooks) match. | Verified with ast-grep 0.51.3. |
| 11 | 2 | `no-print-in-app` is scoped to `**/fixtures/**`, covering both `valid/` and `invalid/`. | `fixtures/invalid/logging/print_debug.py` stands in for application code; scoping to `fixtures/valid/` only would hide the rule from its own invalid fixture. |
| 12 | 2 | `no-manual-init-boilerplate` ships as `warning` and is deliberately narrow: classes whose only method is `__init__`, whose `__init__` only contains `self.x = x` (and comments), and that do not subclass an `*Exception`/`*Error`. Broader detection (e.g. classes with other methods, `self.x = x` mixed with logic) is a Fixit candidate. | Dependency-injection constructors (`self.client = client` plus methods) are legitimate and very common; matching them would be a false positive. |
| 13 | 2 | The `domain_imports_infra.py` test copies `fixtures/valid/` (plus `fixtures/__init__.py`) and `.importlinter` into a pytest `tmp_path` and adds the invalid fixture there, instead of writing into the real `fixtures/valid/domain/`. | Same check, without the risk of leaving a broken file in the working tree if the test is interrupted. |
| 14 | 2 | `.importlinter` uses `root_package = fixtures` and names `fixtures.valid.*` in the contract. | The clean code is a subpackage of `fixtures/`; `fixtures/invalid/<rule>/` folders have no `__init__.py`, so they are not part of the import graph. |
| 15 | 3 | Verified `ast-grep-ignore` for Python: `# ast-grep-ignore: <id>[, <id>]` on the line directly above the code, or trailing on the same line. A bare `# ast-grep-ignore` suppresses every rule, so `check_exceptions.py` rejects it. The `# rule-exception:` comment goes on the line above (above the code line for the trailing form). Comments are found with `tokenize`, so strings that contain the marker are not mistaken for exceptions. | [VERIFY] item. ast-grep also reports `unused-suppression` for an ignore that suppresses nothing. |
| 16 | 3 | **`scripts/check_language.py` was dropped at the user's request.** English-only (principle 1) is enforced as an explicit instruction in every skill, reference and reviewer template, not as a script. `make lint-rules` does not run a language check. | User decision: a heuristic test is not needed; the agent follows the instruction. |
| 17 | 3 | `check_no_domain_leak.py` takes `--exclude <folder>` (repeatable) for tooling code that is not the analyzed project. In this repo `make lint-rules` passes `--exclude scripts --exclude tests --exclude fixtures/invalid`; `fixtures/valid/` is the analyzed code. `fixtures/invalid/<rule>/` is excluded because its folders are named after the rules and its files repeat the rule-test code on purpose. Single-word function names are not collected (too generic); class, module, package, compound function and compound field names and string literals of 16+ characters are. `fixtures` and structural folders are in `generic_names.txt`. | Without `--exclude`, the tooling's own test fixtures and the invalid fixtures (which quote the rules) are reported as leaks. |
| 18 | 3 | `make lint-rules` scans the repo with `--globs '!fixtures/invalid/**'`; `make lint-rules-changed` scans changed files (excluding `fixtures/invalid/`) with `--error`, so `warning` rules fail on new or touched code only. `STAGED=1` switches to staged files; `BASE_REF` overrides `origin/main`, falling back to `main` when there is no remote. | Implements "fail only when a change adds new instances". |
| 19 | 3 | Added `AGENTS.md` with the `rules-table` markers, so `make rules-table` has a target to update. | The plan inserts the table only "if they exist"; one agent file shows the mechanism. |
| 20 | 3 | `scripts/` is grouped by purpose: `guards/` (`make guards`), `generate/` (`make rules-table`), `git/` (`make lint-rules-changed`) and `install/` (`make setup`), with `scripts/README.md` listing every script, what it does and which target runs it. Python tools are a package run with `python -m scripts.<folder>.<name>`, and `rules_table.py` imports from `scripts.guards.<module>`. The plan's later scripts follow the same layout (`hooks/` for the agent hooks, `install/` for the user-rules installers). | PR #5 review: the flat folder read like a barrel of scripts with no clear purpose. Running as modules lets one folder import another without `sys.path` changes. |
| 21 | 4 | The rule checks run in pre-commit as a `repo: local` hook (`make lint-rules-changed STAGED=1`, `always_run`), next to the static checks. `boidolr/ast-grep-pre-commit` is not added. | It would run a second, different invocation of the same scan; the plan requires pre-commit and CI to run the same target. |
| 22 | 4 | No separate `lint-rules.yml` workflow. The `static-checks` job in `ci.yml` runs `make lint` (pre-commit, including the `lint-rules` hook), then `make lint-rules`, `make demo` and `make test`. | The hook runs with `STAGED=1`, and a CI checkout has nothing staged, so the scan has to run on its own. The coverage guard already runs inside the hook through `make guards`. One workflow means one set of required checks. |
